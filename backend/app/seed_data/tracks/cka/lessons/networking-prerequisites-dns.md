## Names instead of addresses

```bash
ping 192.168.1.11      # works, but nobody remembers addresses
ping db                # "db" has to become 192.168.1.11 somehow
```

Two places a Linux host looks, in an order decided by `/etc/nsswitch.conf`
(`hosts: files dns` - files first, then DNS).

## /etc/hosts

```bash
cat >> /etc/hosts <<EOF
192.168.1.11   db
192.168.1.12   web
EOF
ping db            # resolved locally, no network question asked
```

Every host keeps its own file. Works for three machines; a nightmare for
three hundred. The fix is a central server.

## A DNS server and /etc/resolv.conf

```bash
cat /etc/resolv.conf
# nameserver 192.168.1.100
# search mycompany.com prod.mycompany.com
# options ndots:5
```

- `nameserver` - where to ask (up to three; tried in order).
- `search` - suffixes to append when a name has no dots: `ping web` tries
  `web.mycompany.com`, then `web.prod.mycompany.com`.
- `ndots` - a name with fewer than this many dots is tried with the search
  suffixes **first**; with more, it is tried as-is first.

On a modern Ubuntu `/etc/resolv.conf` is generated by `systemd-resolved`
(the nameserver is `127.0.0.53`, a local stub) - `resolvectl status` shows
the real upstreams. Inside a **Pod** the file is written by the kubelet, and
it is what makes `curl api` work from any Pod; that is the DNS-in-Kubernetes
lesson.

## Record types you need to recognise

| Type | Maps | Example |
|---|---|---|
| A | name → IPv4 | `web.example.com → 203.0.113.10` |
| AAAA | name → IPv6 | |
| CNAME | name → another name | `www → web.example.com` |
| SRV | service → host + port | what CoreDNS uses for `_http._tcp.svc` lookups |
| PTR | IP → name (reverse) | `10.113.0.203.in-addr.arpa → web` |

Kubernetes Services are A records (and SRV for named ports); headless
Services return several A records, one per Pod.

## Tools

```bash
nslookup web.example.com               # simple: asks resolv.conf's nameserver
dig web.example.com                    # verbose: every section, the server that answered, TTL
dig @10.96.0.10 api.payroll.svc.cluster.local   # ask a SPECIFIC server (CoreDNS's ClusterIP)
host web.example.com
getent hosts web                       # resolve the way libc does: /etc/hosts THEN DNS
```

`nslookup` and `dig` query DNS **only** - they ignore `/etc/hosts`. `ping`,
`curl`, `getent` go through libc and honour the hosts file and the search
list. When "ping works but dig fails" or the reverse, that difference is the
explanation.

:::exam-tip
Inside a Pod the handy tool is often missing. `busybox` has `nslookup`;
`kubectl run -it --rm t --image=busybox:1.36 -- nslookup kubernetes` is the
universal DNS test. For a full `dig`, use an image like
`registry.k8s.io/e2e-test-images/jessie-dnsutils`.
:::

## Reading a failed lookup

| Output | Means |
|---|---|
| `;; connection timed out; no servers could be reached` | the nameserver in resolv.conf is unreachable (CoreDNS down, NetworkPolicy blocking 53) |
| `** server can't find web: NXDOMAIN` | the server answered: no such name (typo, wrong namespace, missing search suffix) |
| resolves to the wrong address | a stale `/etc/hosts` entry, or a CNAME you did not expect |

Timed out = a **connectivity** problem; NXDOMAIN = a **naming** problem. Keep
them apart and half of DNS debugging is done.

## Check yourself

1. In which order does `ping web` consult `/etc/hosts` and DNS, and what file
   decides that?
2. What does the `search` line in `resolv.conf` do to the name `api`?
3. `nslookup` says "connection timed out" from inside a Pod. Is the name
   wrong, or something else?
