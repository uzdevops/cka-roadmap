## One file is not always the right size

A monorepo with a backend, a frontend and docs; a pipeline whose
structure depends on what changed; a 600-line YAML nobody dares edit. The
fix is **pipelines that start pipelines**: a parent that triggers
**child pipelines** in the same project, or a **multi-project** pipeline
in another.

## Child pipelines

```yaml
# .gitlab-ci.yml (parent)
stages: [triggers]

backend:
  stage: triggers
  trigger:
    include: backend/.gitlab-ci.yml
    strategy: depend                 # parent waits for the child and mirrors its status
  rules:
    - changes: [ "backend/**/*" ]

frontend:
  stage: triggers
  trigger:
    include: frontend/.gitlab-ci.yml
    strategy: depend
  rules:
    - changes: [ "frontend/**/*" ]
```

Each child is a full pipeline with its own stages, shown nested under the
parent (**downstream**). `strategy: depend` makes the parent's trigger job
succeed or fail with the child; without it the trigger job is green the
moment the child *starts*. Variables flow down with `trigger:` →
`variables:` or `forward:`; artifacts flow up only explicitly
(`needs:project`/`needs:pipeline` in the parent's later jobs).

## Dynamic child pipelines

The YAML of a child can be **generated by an earlier job** and passed as
an artifact - the pipeline writes its own pipeline:

```yaml
generate:
  stage: build
  image: python:3.12-slim
  script:
    - python tools/generate-pipeline.py > generated.yml    # e.g. one job per service found on disk
  artifacts:
    paths: [generated.yml]

run-generated:
  stage: test
  trigger:
    include:
      - artifact: generated.yml
        job: generate
    strategy: depend
```

This is how a matrix of services, test suites or terraform workspaces is
driven from *data* rather than maintained by hand.

## Multi-project pipelines

```yaml
deploy-infra:
  stage: deploy
  trigger:
    project: xyz-team/infrastructure
    branch: main
    strategy: depend
  variables:
    APP_IMAGE: "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA"
```

The downstream project's pipeline runs as the triggering user (who needs
permission there) and sees `APP_IMAGE`. Use this for "the app repo hands
off to the platform repo"; use `needs:project:` in the other direction to
pull a specific artifact from another project's job.

## Which to choose

| Need | Use |
|---|---|
| split one big file into parts, same repo | child pipelines with `include:` |
| shape depends on what changed | child + `rules:changes` |
| shape depends on data discovered at run time | dynamic child (artifact) |
| hand off to another repository | multi-project `trigger:project` |
| reuse job definitions without a new pipeline | `include:` / components (next lesson) |

## Self-check

- What changes when you add `strategy: depend` to a trigger job?
- How does a dynamic child pipeline receive its YAML?
- A downstream pipeline in another project fails to start with a permission error - whose permissions?
